# 거래명세서 → 업체 결제요청 초안 직접 작성

자동화 스크립트(`statement_pdf_inspector.py`, `apply_payment_skill.py`)를 끝까지 돌리지 않고
초안만 만들어야 할 때의 절차. 스크립트의 LLM 단계가 느리거나 막혔을 때(쿼터 소진, 제공자 타임아웃)
이 경로로 우회한다.

## 언제 이 경로를 택하는가

- **업체 결제요청**(견적서·전자세금계산서) 초안만 필요 → 스크립트 대신 직접 작성
- 스크립트의 Vision 폴백이 15~25분/파일로 예상될 때
- 지급신청 초안은 `apply_payment_skill.py` 가 시트 매칭을 서명 검증으로 보호하므로 **스크립트를 쓴다**

## 1. 거래명세서에서 추출할 것

거래명세서는 스캔 이미지인 경우가 많다(PyMuNative 텍스트 0자). 추출 순서:

1. `pytesseract` 로 페이지별 OCR(kor+eng) → 공급자·사업자번호·품목·금액 확보
2. **도장 날짜는 OCR로 불안정하다**(도해로 연도가 2025/2024/1994로 읽힌 사례가 반복됨).
   이때는 **인쇄 발행일자를 입고일로 쓴다** — 거래명세서 전체가 인쇄일자 하나를 공유한다.
   도장 판독이 의심되면 그 사실을 보고에 밝힌다.
3. Vision이 필요할 때만 쓴다. Tesseract만으로 거래처·품목·금액이 다 나오면 Vision은 생략한다.

### 거래명세서가 2페이지 이상이면

페이지마다 별도 거래명세서가 stapled된 형태다. 날짜·품목이 다르지만 **같은 업체**이므로
하나의 초안으로 묶는다.

```
[결제] 9/22, 9/28 입고품목에 대한 견적서·전자세금계산서 요청 (브니엘바이오 주식회사)
```

## 2. 합계 계산

- 세액이 표기된 경우: `공급가액 + 세액 = 합계` 로 교차검증. 안 맞으면 문서를 다시 본다.
- **세액 미표기**: 공급가액 = 합계. 10%를 가산하지 않는다(가산하면 제목과 본문이 어긋난다).

## 3. 수신자 확정

| 상황 | 처리 |
|---|---|
| 거래명세서에 이메일 인쇄 | 그대로 사용 |
| Sheets `업체정보`/과제 시트에 있음 | 사용 |
| 스킬 `DEFAULT_SUPPLIERS` 맵에 있음 | 사용(출처를 로그에 남김) |
| 아무 데도 없음 | 본인 주소로 두고 본문 상단에 `[수신자 미상]` 경고 |

**To 헤더를 비우면 Gmail이 `400 Invalid To header` 로 400을 반환한다.** 빈 To로는 초안을 못 만든다.

## 4. 본문 형식

### 결제요청(견적서·전자세금계산서) — 회신 절차 있음

품목표(입고일·제조사·Cat. No·제품명·규격·수량·단가·공급가액)를 HTML 테이블로 넣고,
하단에 합계와 요청 서류 2항목(견적서 1부 / 전자세금계산서 1부)을 명시한다.
`msg.add_alternative(html)` 으로 plain-text와 HTML을 함께 넣는다.

### 지급신청 — 회신 절차 없음

`gmail-draft-automation` SKILL.md의 4b 절을 따른다(4줄 plain-text 단독).

## 5. 생성 후 검증

```python
d = svc.users().drafts().get(userId="me", id=draft_id, format="full").execute()
h = {x["name"]: x["value"] for x in d["message"]["payload"]["headers"]}
```

- `drafts.list()` 로 확인하지 않는다 — 생성 직후 0건을 반환하는 구간이 있다.
- 첨부 목록·제목·To를 read-back으로 확인한 뒤 성공으로 보고한다.
